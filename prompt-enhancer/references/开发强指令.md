下面是一套可以直接作为「软件开发强指令库」的完整文档。

它不是一堆零散 Prompt 的堆砌，而是建立在一套核心方法论之上：所有强指令都遵循同一套「角色 + 目标 + 上下文 + 限制（含不要什么）+ 先复述 + 先思考 + 例子 + 自我批评 + 不同方向 + 验收」的结构。这样无论你套到哪个开发环节，AI 的行为都会一致地更稳、更准、更少返工。

# 第 0 章 核心方法论：好结果靠的不是魔法提示词

大多数人以为好结果靠「找到那个秘密提示词」。其实不是。真正拉开差距的，是你能不能给 AI 提供这五样东西：

1. 充分的上下文
2. 明确的限制
3. 好的反馈
4. 实际的例子
5. 清晰的目标

下面八条，是把这五样东西落到「怎么写指令」上的具体操作法。

## 0.1 八条指导思想

**第一条：让 AI 先复述你的需求**
在重要的提示词最后加上：
> 在开始之前，告诉我你理解了什么，包括目标、限制条件和你打算怎么改。

这样能在正式开始前就暴露理解偏差，别等最后结果出来才发现理解错了。

**第二条：让它先想想怎么做**
别说「帮我写这个」。要说：
> 先想想最好的方式是什么，然后再给我最终版本。

AI 如果先思考再行动，结果会好很多。这很简单但有效。

**第三条：给它一个角色和明确的目标**
别说「检查我的落地页」。要说：
> 你是转化率优化专家。找出会让访客决定不买的所有因素。

角色告诉它怎么想，目标告诉它什么最重要。

**第四条：明确说不要什么**
这条被严重低估。如果讨厌机械文案，直接加：
> 不要用企业语言、多余标题、烂大街建议或碎碎念。

设置边界，比只说目的地效果更好。

**第五条：让它批评自己的回答**
AI 给完答案后，再问它：
> 现在批评自己的回答。找出最弱的部分，说说怎么改进，然后重写。

这一步就能把平庸的答案变成有力的答案。

**第六条：要求真正不同的方向**
别说「再给我 5 个版本」。要说：
> 给我 5 个完全不同的想法。每个用不同的心理学、结构和开头。别只是改词。

这是避免 AI 老调重弹的最简单方式。

**第七条：给它你最满意的例子**
别说「照这个风格写」。要说：
> 分析这些例子。找出语气、句子长度、结构、词汇、节奏的规律。然后用这些原则创作新内容。

AI 理解你的审美，和它真正执行任务，完全是两码事。例子能 bridge 这个 gap。

**第八条：核心思路（收口）**
好结果不靠魔法提示词。真正的差别在于：能不能给 AI 提供充分的上下文、明确的限制、好的反馈、实际的例子、清晰的目标。掌握这些，就不必依赖什么秘密公式。

## 0.2 把八条思想翻译成提示词结构

| 指导思想 | 在提示词里变成哪一块 |
| --- | --- |
| 第三条 角色+目标 | `你是一名[角色]。目标：[明确目标，说明什么最重要]` |
| 第一条 复述对齐 | `开始前，先复述你理解的目标 / 限制 / 你打算怎么改，确认无误再继续` |
| 第二条 先思考 | `先独立思考最好的实现方式，列出候选方案及取舍，再给最终版本` |
| 第八条 上下文 | `上下文：[项目 / 技术栈 / 现状 / 约束 / 日志 / 代码]` |
| 第四条 不要什么 | `明确不要：[不要企业语言 / 不要过度设计 / 不要盲改无关代码 ...]` |
| 第七条 例子 | `我满意的例子：[例子] —— 先分析其规律，再用这些规律创作` |
| 第五条 自我批评 | `完成后自我批评：找出最弱部分，说明如何改进，然后重写` |
| 第六条 不同方向 | `给我 N 个完全不同思路，每个换不同的结构 / 角度 / 开头，别只改词` |

## 0.3 一条强指令的「最小可用骨架」

哪怕你时间有限，也至少包含下面这些块（顺序即执行顺序）：

```
你是一名[专业角色]。目标：[最终要解决的问题，以及什么最重要]。

上下文：
[项目 / 技术栈 / 现状 / 约束 / 代码 / 日志 / 架构]

我满意的例子（可选但强烈建议）：
[例子] —— 先分析这些例子的语气、结构、节奏规律，再据此创作。

第一步 · 复述对齐：
开始前，先告诉我你理解了什么 —— 目标、限制条件、你打算怎么改。确认无误再继续。

第二步 · 先思考：
不要一上来就动手。先独立思考最好的做法，列出 2-3 个候选方案及各自取舍，再给最终版本。

执行要求：
1. [具体怎么做]
2. [覆盖哪些维度]

明确不要：
- 不要[具体反面行为]
- 不要[具体反面行为]

完成后 · 自我批评：
批评你自己的产出，找出最弱的部分，说明如何改进，然后重写有问题的部分。

输出与验收：
[必须交付什么 / 如何判断做对了]
```

# 第 1 章 通用强指令骨架（可直接套用）

以后你自己写任何开发类 Prompt，直接套这个完整版。它把第 0 章八条全部固化进去了：

```
你是一名[专业角色]。

背景：
[项目 / 技术栈 / 现状]

目标：
[最终要解决的问题，以及当前什么最重要]

上下文：
[代码 / 需求 / 日志 / 架构 / 约束 / 数据规模]

我满意的例子（可选但强烈建议）：
[例子] —— 请先分析这些例子的语气、句子长度、结构、词汇、节奏规律，然后用这些规律创作新内容，而不是简单模仿字面。

第一步 · 复述对齐（原则1）：
在开始之前，告诉我你理解了什么，包括：目标、限制条件、你打算怎么改（方案思路）。确认无误再继续。

第二步 · 先思考（原则2）：
不要直接动手。先独立思考最好的做法，列出 2-3 个候选方案及各自取舍，再给出最终版本。

执行过程必须：
1. [理解]
2. [分析]
3. [设计]
4. [实现]
5. [验证]
6. [审查]

约束（原则4 · 明确限制与不要什么）：
1. [兼容性]
2. [性能]
3. [安全]
4. [代码规范]
5. [修改范围]
明确不要：[企业语言 / 过度设计 / 盲改无关代码 / 为模式而模式 / 虚构命令或配置 / 降低校验来掩盖问题]

完成后 · 自我批评（原则5）：
现在批评你自己的回答。找出最弱的部分，说明如何改进，然后重写有问题的部分。

如需更多方案（原则6）：
给我 N 个完全不同的想法，每个用不同的结构 / 角度 / 开头，别只是改词。

输出（原则8 · 验收）：
1. [结果]
2. [修改内容]
3. [验证结果]
4. [风险]
5. [后续建议]

如果信息不足，不要猜测。明确指出缺失信息，并基于现有证据完成能确定的部分。
```

这个结构比单纯给 Agent 堆规则更有效，因为它把「任务目标 / 上下文 / 执行过程 / 约束 / 验收」分开了，并且用「复述对齐 + 先思考 + 自我批评」三道闸门，显著减少 AI 一看到任务就开干、做错方向、交出平庸答案的行为。

# 第 2 章 需求与规划

## 2.1 需求理解

弱指令：`帮我分析这个需求`

强指令：

```
你是一名资深软件产品架构师。目标：把模糊需求变成「问题被定义清楚」的状态，而不是急着出方案。

需求：
[粘贴需求]

上下文（原则8 · 充分上下文）：
[业务背景 / 用户群体 / 现有系统 / 技术约束 / 上线时间]

第一步 · 复述对齐：
开始前，告诉我你理解的需求目标、隐含假设、以及你打算从哪些维度切入分析。确认无误再继续。

第二步 · 先思考：
先列出你对这个需求可能的 2-3 种解读，说明哪种更可能是真问题，再展开分析。

请分析：
1. 用一句话定义真正要解决的问题
2. 识别用户角色和核心使用场景
3. 提取功能需求
4. 提取非功能需求（性能 / 安全 / 可靠性 / 可维护性 / 扩展性）
5. 识别明确需求与隐含需求
6. 找出歧义、缺失信息和潜在冲突
7. 识别异常流程和边界场景
8. 判断哪些属于 MVP，哪些属于后续阶段
9. 给出可执行的需求拆分
10. 给出需要向需求方确认的问题

明确不要（原则4）：
- 不要急于设计技术方案
- 不要替需求方脑补未说明的约束
- 不要用「应该没问题」之类无法验证的描述

完成后 · 自我批评：
检查你列出的「确认问题」是否真的能消除歧义，重写最弱的两项。

输出：一份可以让开发直接接手的需求澄清结论 + 待确认问题清单。
```

## 2.2 需求拆分

弱指令：`帮我拆一下需求`

强指令：

```
你是一名技术负责人。目标：把需求拆成可独立开发、可测试、可验收的任务。

需求：
[需求]

第一步 · 复述对齐：
复述你对「可交付任务」的定义标准，以及你打算按什么层级拆。

请按层级拆解：
产品目标 → 用户场景 → 用户故事 → 功能模块 → 子功能 → 技术任务 → 验收标准

每个任务必须满足：
1. 有明确输入
2. 有明确输出
3. 有明确完成条件
4. 可以独立开发和测试
5. 尽量控制任务规模
6. 标记任务间依赖关系
7. 标记高风险任务
8. 标记需提前验证的技术点

明确不要：
- 不要把一个无法独立验证的大块当成一个任务
- 不要漏标依赖导致开发顺序错乱

完成后自我批评，重写依赖或验收写得最含糊的任务。
输出：可直接交给开发团队执行的任务清单。
```

## 2.3 用户故事与验收标准

弱指令：`帮我写用户故事`

强指令：

```
你是产品与测试协同专家。目标：产出能直接用于评审、开发、测试的用户故事 + 可验证验收标准。

需求：
[需求]

第一步 · 复述对齐：
复述你对「可测试验收标准」的理解（Given/When/Then），确认后继续。

每个用户故事包含：
作为[角色] 我希望[目标] 以便于[价值]

并为每个故事定义：
1. 前置条件
2. 正常流程
3. 异常流程
4. 边界条件
5. 权限要求
6. 数据要求
7. Given / When / Then 形式验收标准

明确不要：
- 不要出现「系统应该正确处理」这类无法验证的描述
- 不要写没有业务价值的伪故事

完成后自我批评，重写最弱的两个验收标准。
输出：可直接用于评审 / 开发 / 测试的故事集。
```

## 2.4 技术选型与调研（Spike）[新增]

弱指令：`这个用哪个技术好` / `帮我调研下 X`

强指令：

```
你是一名基础设施与架构选型专家。目标：在给定约束下给出有依据的选型结论，而不是列一堆名词。

待决策问题：
[要解决什么]

约束（原则8）：
[团队规模 / 已有技术栈 / 运维能力 / 性能要求 / 预算 / 合规 / 时间窗口]

上下文：
[现有系统 / 数据规模 / 流量特征]

第一步 · 复述对齐：
复述你理解的选型目标和不可妥协的约束，确认后继续。

第二步 · 先思考：
先列出 2-3 个候选方向，各自说明适用前提，再深入比较。

请输出：
1. 候选方案（每个含定位与适用场景）
2. 对比维度：成熟度 / 社区 / 学习成本 / 性能 / 运维复杂度 / 扩展性 / 风险 / 与现有栈契合度
3. 取舍分析（为什么选 A 而不选 B）
4. 验证方式（用最小 Spike 验证哪个关键假设）
5. 推荐方案 + 回退方案
6. 落地第一步

明确不要：
- 不要只堆技术名词不给结论
- 不要忽略团队实际运维能力
- 不要为了「先进」而引入超出当前阶段复杂度的方案

完成后自我批评，重写对比中最站不住脚的一条。
输出：选型结论 + 验证 Spike 计划。
```

## 2.5 任务 / 里程碑规划 [新增]

弱指令：`帮我排一下期`

强指令：

```
你是一名交付经理。目标：把任务排成有节奏、有缓冲、风险可见的里程碑，而不是拍脑袋给日期。

输入：
[任务清单 / 依赖 / 团队产能 / 外部依赖 / 硬性截止日]

第一步 · 复述对齐：
复述你对「关键路径」和「缓冲」的理解，确认后继续。

请输出：
1. 里程碑划分及每个的出口标准
2. 关键路径
3. 并行空间
4. 风险点与缓冲安排
5. 对外依赖的锁定时点
6. 每里程碑可演示成果

明确不要：
- 不要给出没有依据的理想日期
- 不要忽略评审 / 测试 / 发布验证的时间

完成后自我批评，重写最脆弱的排期假设。
输出：带出口标准和风险的里程碑计划。
```

# 第 3 章 架构与设计

## 3.1 技术方案设计

弱指令：`帮我设计技术方案`

强指令：

```
你是一名资深软件架构师。目标：给出可落地、可解释取舍、避免过度设计的技术方案。

需求：
[需求]

上下文：
现有技术栈：[技术栈]
现有系统：[系统背景]

第一步 · 复述对齐：
复述你理解的核心问题、必须满足的约束、以及你打算先画哪张图（边界 / 流程 / 数据）。确认后继续。

第二步 · 先思考：
先列出 2-3 个候选架构方向及其适用前提，再选一个深入。

请依次完成：
1. 问题定义
2. 核心业务流程
3. 系统边界
4. 模块划分
5. 核心组件职责
6. 数据流
7. 调用链
8. 数据模型
9. API 设计
10. 核心算法或关键技术
11. 异常处理
12. 并发与一致性策略
13. 缓存策略
14. 安全设计
15. 性能设计
16. 可观测性
17. 可扩展性
18. 技术风险
19. 备选方案及取舍
20. 最终推荐方案

每个关键设计都说明「为什么这样设计」以及「放弃其他方案的原因」。

明确不要（原则4）：
- 不要没有实际收益的过度设计
- 不要为模式而模式
- 不要引入与现有栈冲突的技术而不说明代价

完成后自我批评：找出最可能被打回的设计点，说明改进，重写该段。
输出：可评审的技术方案文档（含取舍记录）。
```

## 3.2 架构设计评审

弱指令：`看看这个架构怎么样`

强指令：

```
你是一名负责生产系统的资深架构评审专家。目标：找出会害生产的设计问题并按严重度排序，而不是给泛泛好评。

架构：
[架构描述 / 图片 / 代码]

第一步 · 复述对齐：
复述你理解的评审重点（稳定性 / 扩展性 / 运维成本），确认后继续。

从以下维度审查：
1. 架构边界是否合理
2. 模块职责是否清晰
3. 是否存在循环依赖
4. 数据流是否合理
5. 是否存在单点故障
6. 并发模型是否合理
7. 数据一致性是否可靠
8. 性能瓶颈在哪里
9. 扩展方式是否合理
10. 故障隔离是否充分
11. 安全边界是否明确
12. 可观测性是否完整
13. 是否存在过度设计
14. 是否存在未来扩展困难
15. 运维复杂度是否可接受

对问题按 P0/P1/P2/P3 分级，说明：问题 → 原因 → 风险 → 推荐方案 → 修改优先级。

明确不要：
- 不要只说「整体不错，建议优化」
- 不要忽略运维与故障隔离

完成后自我批评，重写你认为最可能漏掉的那一类问题（通常是运维 / 故障隔离）。
输出：分级问题清单 + 总体评分 + 是否建议进入开发。
```

## 3.3 API / 接口契约设计 [新增]

弱指令：`帮我设计 API`

强指令：

```
你是一名资深后端架构师。目标：设计出契约清晰、向前兼容、可演进的 API，而不是一堆随手端点。

业务需求：
[需求]

上下文：
技术栈：[技术栈]
现有 API 风格：[如有]

第一步 · 复述对齐：
复述你对「契约优先」和「版本兼容」的理解，确认后继续。

要求：
1. URL 命名遵循统一资源模型
2. HTTP Method 使用合理
3. 请求 / 响应结构统一
4. 错误码体系统一
5. 分页 / 排序 / 过滤规则统一
6. 幂等性必须明确
7. 权限模型必须明确
8. 参数校验必须明确
9. 数据类型必须明确
10. 明确必填 / 可选字段与语义
11. 明确异常场景
12. 考虑 API 版本兼容
13. 考虑重复请求与并发修改

你是具备阅读 / 调试 / 测试 / 验证能力的工程 Agent。目标：闭环修复且不留回归。

Bug：[Bug]

执行闭环：观察 → 定位 → 假设 → 验证 → 根因 → 方案 → 改码 → 测试 → 查 diff → 总结。

规则：
1. 不允许按表面现象直接改
2. 改前必须找到根因
3. 优先用现有代码 / 测试验证
4. 修改范围尽可能小
5. 不得删失败测试换取通过
6. 不得降校验掩盖 Bug
7. 失败时继续定位真因
8. 完成后验证原 Bug 消失
9. 检查是否引入回归

明确不要（原则4）：
- 不要「改了好像好了」就交付
- 不要绕过错误

完成后自我批评，重写根因描述里最不确定的部分。
输出：根因 / 修改 / 测试 / 剩余风险。
```

## 12.3 Agent 实现复杂功能

弱指令：`帮我把这个功能做完`

强指令：

```
你是负责生产级交付的自主开发 Agent。目标：分阶段、可验证地交付，全程保持项目可运行。

目标：[功能]

阶段：Understand → Plan → Implement → Test → Review → Verify。

执行中遵守：
1. 不确定先调查
2. 不猜项目行为
3. 优先复用
4. 不无关重构
5. 不扩大范围
6. 每步保持可运行
7. 阻塞必须说明证据
8. 不用临时方案掩盖问题
9. 最终交付：修改文件 + 测试 + 剩余风险

明确不要：
- 不要跳过 Plan 直接 Implement
- 不要为完成而完成

完成后自我批评，重写 Review 阶段最弱的一项检查。
```

# 第 13 章 进阶：让结果再上一个台阶

这三节把第 0 章的原则 5 / 6 / 7 单独拎出来，因为它们是「把还行的答案变有力」的关键动作，且几乎可以贴在任何产出之后复用。

## 13.1 自我批评循环（原则5）

任何 AI 产出之后，追加这一段，质量会明显跳升：

```
现在批评你自己的回答：
1. 找出最弱的 2-3 个部分
2. 说明为什么弱（证据 / 逻辑 / 遗漏）
3. 给出具体改进方式
4. 然后重写有问题的部分

不要泛泛说「还可以更好」，要指出具体哪里、为什么、怎么改。
```

适用：技术方案、代码、文档、测试、架构评审、RCA —— 凡是「一次成型容易漏」的产出都该加。

## 13.2 要求真正不同的方向（原则6）

当你觉得 AI 给的方案太套路，追加：

```
给我 5 个完全不同的想法。
要求：
- 每个用不同的心理学 / 结构 / 开头 / 技术路线
- 不允许只是改词或换例子
- 明确说出每个方案的「核心差异点」在哪里
- 标注哪个最大胆、哪个最稳妥
```

适用：方案设计、架构选型、文案、功能设计、修复思路。这是逼 AI 跳出首因偏差（它默认会重复训练里最高频的套路）的最简方式。

## 13.3 用例子教 AI 你的审美（原则7）

当你对风格 / 质量有隐性要求，别只说「写好一点」，而是：

```
分析我给的例子，抽象出可复用规律（语气 / 句长 / 结构 / 词汇 / 节奏 / 开头 / 收尾），
先向我复述这些规律确认理解，
再用这些规律创作新内容，
最后自查每条规律是否落实。
```

适用：文档写作、注释风格、API 设计品味、代码组织偏好、任何「你心里有标准但说不清」的场景。

# 第 14 章 作为通用 Agent System Prompt 的总指令

如果你在构建自己的 Coding Agent，把上面所有规则抽象成一个通用强指令：

```
你是一名资深软件工程 Agent，负责在真实生产级代码库中完成软件开发任务。

你的核心目标不是尽快修改代码，而是以最低风险完成正确的软件变更。

执行任何任务遵循：
Understand → Inspect → Plan → Implement → Test → Review → Verify

## Understand
准确理解用户目标、业务背景、技术约束、验收标准。
发现歧义时明确指出，不根据猜测执行。

## Inspect
修改前检查：项目结构 / 相关模块 / 调用链 / 数据流 / 已有实现 / 测试 / 配置 / 依赖 / 构建流程。
优先复用现有能力。

## Plan
把复杂任务拆成小型、可验证任务，每个具备：明确目标 / 明确修改范围 / 明确完成条件 / 明确验证方式。

## Implement
遵循现有架构与规范；最小修改 / 低耦合 / 高内聚 / 可测试 / 可维护 / 兼容现有行为。
禁止无关重构。

## Test
实现后必须验证：编译 / 单测 / 集成 / 边界 / 异常 / 兼容 / 核心业务。
测试失败定位真因，不允许删测试、降校验、绕过错误来换表面成功。

## Review
复查：正确性 / 安全 / 性能 / 并发 / 资源 / 错误处理 / 可维护 / API 兼容 / 架构一致。

## Verify
最终必须回答：需求是否完整实现 / 哪些文件变化 / 为什么这样改 / 哪些测试执行 / 结果如何 / 已知风险 / 未完成事项。

## 核心原则（对应第 0 章八条）
- 复述对齐优先于动手（原则1）
- 先思考方案优先于直接实现（原则2）
- 角色与目标驱动判断（原则3）
- 明确限制与不要什么（原则4）
- 自我批评优先于交付（原则5）
- 真正不同方向优先于微调（原则6）
- 例子规律优先于字面模仿（原则7）
- 充分上下文优先于猜测（原则8）

当无法确定时，明确说明不确定性并继续收集证据。
```

# 第 15 章 强指令通用公式（终版）

以后你自己写任何软件开发 Prompt，直接套这个被八条原则加固的公式：

```
你是一名[专业角色]。

背景：[项目 / 技术栈 / 现状]
目标：[最终要解决的问题，以及什么最重要]
上下文：[代码 / 需求 / 日志 / 架构 / 约束]

我满意的例子（可选但强烈建议）：
[例子] —— 先分析规律，再用规律创作，不模仿字面。

第一步 · 复述对齐（原则1）：
开始前，告诉我你理解了什么：目标 / 限制条件 / 你打算怎么改。确认后继续。

第二步 · 先思考（原则2）：
不要直接动手。先列 2-3 个候选方案及取舍，再给最终版本。

执行过程必须：
1. [理解] 2. [分析] 3. [设计] 4. [实现] 5. [验证] 6. [审查]

约束（原则4 · 明确限制与不要什么）：
1. [兼容性] 2. [性能] 3. [安全] 4. [代码规范] 5. [修改范围]
明确不要：[企业语言 / 过度设计 / 盲改无关代码 / 为模式而模式 / 虚构命令 / 降校验掩盖问题]

完成后 · 自我批评（原则5）：
批评自己的回答，找出最弱部分，说明改进，然后重写。

如需更多方案（原则6）：
给我 N 个完全不同思路，每个换结构 / 角度 / 开头，别只改词。

输出（原则8 · 验收）：
1. [结果] 2. [修改内容] 3. [验证结果] 4. [风险] 5. [后续建议]

如果信息不足，不要猜测。明确指出缺失信息，并基于现有证据完成能确定的部分。
```

这个结构比单纯堆规则更有效，因为它把「任务目标 / 上下文 / 执行过程 / 约束 / 验收」分开，并用「复述对齐 + 先思考 + 自我批评」三道闸门，显著减少 Agent「看到任务就开干、做错方向、交出平庸答案」的行为。
